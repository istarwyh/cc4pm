# Lesson 17.13: Railcode 设计实战——强度谱、原型分叉与参数 Playground

> **前置课程**：Lesson 17.2（AI 原型实验室）、Lesson 17.8（品牌资产与设计交付）、Lesson 17.12（概念驱动的 App 设计）
>
> **预计用时**：20 分钟
>
> **适合人群**：已经能让 AI 写页面，但希望更主动地探索视觉方向、保留比较证据的产品主理人
>
> **实操须知**：在新的 Claude Code session 中操作。详见 [practice-notice.md](../shared/practice-notice.md)。

## 学习目标

- 用视觉强度谱组织探索，区分概念不成立与表达力度不合适
- 保留原型分叉、生成指令和比较理由，能够回退和复用局部发现
- 通过参数 Playground 直接调色、字号与位置，再把结果收敛为设计规则
- 用视觉锚点、区段过渡和上下文导航连接整页，最后再工程化

## 来源与课程边界

本课依据 Yakko Majuri 的 [Railcode 网站设计复盘](https://railcode.dev/blog/vibe-coded-website)，文章标注日期为 2026-08-10，访问日期为 2026-10-30。

作者从品牌含义和用户感受推导出游乐园意象，展示了大量被放弃的探索。他不是一轮提示词生成成品：单个视觉资产放进模板时仍然突兀，后来才通过场景、区段颜色与细节迭代形成整体。

文章描述的是个人创作经验，不是设计质量的对照实验。作者对 Anthropic、Fable 与其他模型的比较是个人偏好，本课不据此推导模型排名，也不把“看起来像设计师做的”当成业务效果证明。

以下植物交换活动页、提示词、目录与验收方法均为 **cc4pm 原创练习**。借用探索方法，不复制 Railcode 的像素资产、游戏画面、代码或品牌。

## Step 1：让探索覆盖一条强度谱

Lesson 17.12 用三版主屏帮助你选方向。本课再补一件事：你做的几版是否真的探索了不同的表达力度，还是三个几乎相同的默认模板？

作者通常尝试至少四版，有时更多；部分给定约束，部分留给 Agent 自由发挥。这个数量描述的是他的习惯，不是课程硬指标。

练习产品是社区植物交换活动页，用户任务固定为“看懂时间地点，选择一株植物并报名”。你先提出“社区温室”的概念，再安排四个小型首屏实验：

| 实验 | 探索维度 | 保持不变的内容 |
|------|----------|----------------|
| 克制版 | 以字阶、留白和少量线条表达温室秩序 | 标题、时间、地点、植物和报名入口 |
| 中等版 | 加入有语义作用的植物分区和导视 | 同上 |
| 强表达版 | 更明显的空间层次与场景过渡 | 同上 |
| 自由实验 | Agent 提一个你没预设的表现方式，并解释理由 | 核心任务仍须可完成 |

所有方向都不满意时，回查概念与用户任务是否有关系；只有强表达版太花时，先调力度，不必立刻推翻概念。

```text
请读取当前品牌与组件约束，为社区植物交换活动页做四个首屏实验。
前三版沿“克制 → 中等 → 强表达”变化，第四版自由探索。
固定活动内容、主要任务和报名入口，不加虚构背书或统计。
每版说明探索假设、哪些选择服务任务、哪些可能只是装饰。
先生成独立预览，不覆盖现有页面。
```

探索预算由你根据项目定。多出版本是为了获取新的判断依据，不能把“生成更多”本身当成进度。

## Step 2：保留可回退的 HTML 分叉

作者在方向基本确定前保持单文件 HTML，方便复制后只改一两项并排看；之后才转成 React 组件。他还保留早期原型及其生成指令，后来能从弃案中找回有用的局部设计。

这里的 fork 指**设计副本**，不等于 Claude 会话 fork，也不要求创建 GitHub fork。单文件适合短期视觉实验，不是生产架构规定。

你可以按下面的方式保存自己的实验：

```text
experiments/plant-swap/
├── index.html             # 预览索引，链接所有实验
├── 01-base.html           # 不覆盖的基线
├── 02-section-color.html  # 只改变区段颜色
├── 03-cta-layout.html     # 只改变主行动布局
├── playground.html        # 参数调整面板
└── decisions.md           # 父版本、指令、差异、判断与保留项
```

`decisions.md` 至少写清：

```text
实验：03-cta-layout
父版本：01-base
问题：用户看完活动时间后，报名入口距离太远
改动：只调整 CTA 的位置与相邻留白
观察：移动端可立即看到入口；长标题下仍需检查
决定：保留布局，颜色继续沿用基线
可复用发现：按钮与日期可以组成同一行动区域
```

这是课程建议的追踪格式，不是作者提供的工具。视觉比较时固定内容和视口，避免同时改文案、配色、布局后无法解释结果。

保存探索历史不代表把全部弃案打包发布。你可以在实验目录或版本历史留档，生产包只包含选定产物。

## Step 3：用 Playground 缩短参数反馈回路

有些问题不值得每次都向 Agent 描述：“再浅一点”“再往上一点”。作者会做 Playground，直接调整配色、文字、位置等变量并实时观察。

下面是一个可以嵌入自建原型的最小练习片段。它只演示局部颜色变量调整，不是 Railcode 原站代码，也没有完整保存功能：

```html
<style>
  #scene { --ground: #dbe8c7; background: var(--ground); padding: 2rem; }
</style>
<label>植物区域底色 <input id="ground" type="color" value="#dbe8c7"></label>
<section id="scene">
  <h1>周六，带一株植物来交换</h1>
  <p>社区活动室 · 14:00–16:00</p>
  <button type="button">报名参加</button>
</section>
<script>
  document.querySelector('#ground').addEventListener('input', event => {
    document.querySelector('#scene').style.setProperty('--ground', event.target.value);
  });
</script>
```

继续练习时，让 Agent 添加文字色、强调色、标题字号、区段间距等**有限变量**，并提供导出当前值的按钮。导出与保存是本课程的扩展要求，不是对作者工具功能的描述。

调完后记录选中的变量值，让 Agent 回填到正式样式或现有设计 Tokens。不要仅凭“看起来舒服”验收；每次换底色也要复查文本、按钮和焦点态的对比与可见性。

## Step 4：从一个视觉锚点扩展成完整页面

作者先选中满意的过山车，再以它约束其他资产，逐步把场景连接到整站。值得学的是锚点的作用，不是所有网站都要游乐园。

对你的植物交换页，锚点可以是一张自绘植物标签。你记录它的线条、色阶、边缘、文字层级与动效力度，后续导视和卡片都能引用同一组约束。

| 检查对象 | 应回答的问题 | 本练习的验收建议 |
|----------|--------------|------------------|
| 视觉资产 | 是否与其他元素共享线条、色彩和空间语言？ | 去掉后如果任务不受影响，说明保留理由 |
| 区段衔接 | 是孤立装饰条，还是帮助内容从一段进入下一段？ | 首屏与活动列表之间没有突兀断层 |
| 导航背景 | 是否适应当前内容区段，同时保持可辨认？ | 滚动切换时文字、焦点和主按钮仍清楚 |
| 动效 | 是否引导视线或表达状态？ | 不遮挡阅读，不成为报名路径的前置等待 |

文章中的导航会随可见区段改变背景。你采用这种方式前，要验证不同底色下的文字对比、滚动边界与移动端菜单；不是只把背景色跟着换。

减少动态效果、焦点检查和移动端测试是本课的验收补充。不要因为原文展示了某个动画，就假定它的所有可用性状态已经得到证明。

## Step 5：方向稳定后再工程化

不要过早把每个弃案都抽象成通用组件。先确定保留方向与变量，再按照项目现有技术栈拆分布局、资产、样式和交互。

你应该给工程阶段留下：

- 选中的基线与代表性截图，以及关键取舍的记录。
- 固定的视觉约束和参数值，避免下次修改又回到默认模板。
- 需要复用的组件与资产清单，以及可删除的实验依赖。
- 仍未验证的状态、性能和无障碍问题。

参考其他网站时说明你借鉴的是哪种关系，例如内容与插画的衔接、区段过渡或 CTA 层级；用自己的品牌、文案和素材重新实现。原文展示的游戏截图和第三方站点不因此变成可自由复用资产。

## 实操与验收

完成植物交换页的首屏探索，并选择其中一个方向：

1. 保留强度谱实验及预览索引，每版都有不同的假设。
2. 从基线复制一版，只改一两项并留下比较记录。
3. 用 Playground 调至少三项变量，保存选定值。
4. 用选定锚点补一个后续区段，检查与首屏的连接。
5. 在桌面、手机、长标题和减少动态效果场景检查报名路径。

这是一套学习练习，不要求无限迭代。你可以在新版本不再解决已记录问题、或只是在交换偏好时停止，先让真实用户完成任务，再决定下一轮投入。

## FAQ

**Q：这是 App Designer 三版流程的替代方案吗？**

不是。Lesson 17.12 组织方向选择；本课补充怎样扩展探索范围、保留分叉和快速调参数。小项目可以只做必要的几个版本。

**Q：HTML 原型最终一定要转 React 吗？**

不必。那是作者的工作路径。你的交付可以是静态页面或现有应用；遵循项目技术栈和发布要求，不能用“原型方便”替代生产质量检查。

**Q：可以直接照文章选模型吗？**

把它当作候选经验，用自己的任务、成本与可用模型做小范围比较。文章没有给出足以证明跨任务模型优劣的评测。
