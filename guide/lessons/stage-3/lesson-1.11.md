# Lesson 17.11: 营收加权的 App 设计逆向——从真实流程提炼设计语法

## 本课目标

完成本课后，你将能够：

- 把高营收应用库当作**带经营信号的设计证据库**，而不是灵感画廊
- 从完整 Flow、单类 Screen 和 UI Element 三个层级研究竞品
- 用跨应用对比提炼品类的共同语法、优秀边缘和差异化机会
- 把研究结果写成可执行的设计规范，而不是一堆截图收藏
- 让 Agent 通过 AppLlama MCP 执行研究，同时遵守访问、版权和归因边界

> **前置知识**：你已经了解 WDS 的竞品逆向入口（Lesson 17）和 UI 模式词典（Lesson 17.1）。本课解决下一步问题：面对数万张真实界面，怎样研究才不会变成“看了很多，但仍然不会设计”。

## 为什么“高营收截图”比普通灵感图库多一层价值

普通设计图库主要回答：**什么看起来不错？**

AppLlama 这类资源还提供应用收入、下载量、评分、界面和流程之间的关联，因此可以继续追问：

- 哪些模式出现在已经获得市场结果的产品中？
- 同一品类的高营收应用，在首次打开、引导、付费墙和主界面上有哪些共性？
- 某个模式只是视觉偏好，还是与转化、留存或任务完成有关？

截至 2026-09-23，AppLlama 官网展示约 **1,255 款应用和 54,444 张界面**，并按 Welcome、Onboarding、Paywall、Home、Settings、Empty State 等 25 类 Screen 组织内容。数字会继续增长，使用时以官网实时页面为准。

但要记住一条重要边界：

> **营收是筛选上下文，不是因果证明。**

一款应用营收高，不等于它的每个界面都优秀；一个付费墙出现在高营收应用里，也不等于它单独造成了营收。你需要判断这个界面是否真的接近产品的增长机制，并用多款应用交叉验证。

## 三个研究层级：Flow、Screen、Element

### 1. Flow：研究完整旅程

当问题是“赢家怎样组织这段体验”时，研究单位应该是 Flow，而不是单张截图。

高价值 Flow 包括：

| Flow | 重点观察 |
|------|----------|
| Welcome | 前 5 秒传达什么，如何进入核心价值 |
| Onboarding | 总步数、每步索取什么、回报什么、何时请求权限 |
| Paywall | 出现位置、试用表达、价格锚点、权益与社会证明 |
| Sign up & login | 先体验还是先注册，退出和返回如何处理 |
| Home | 信息层级、首要行动、下一步是否一眼可见 |
| 品类核心 Flow | 健身训练、记账、语言练习、照片编辑等核心任务 |

研究 3–5 款同品类应用的同一 Flow，记录：

1. 共同骨架：大多数应用都保留哪些步骤？
2. 摩擦分布：哪里刻意增加承诺，哪里主动降低阻力？
3. 导航语法：页面是 push、modal、sheet 还是 overlay？返回会发生什么？
4. 关键分歧：优秀应用在哪些位置采用不同策略？
5. 缺口：所有竞品都没解决好的问题是什么？

### 2. Screen：研究一种页面怎样被解决

当问题是“我们的空状态/进度页/付费页应该怎样组织”时，按 Screen 类型横向搜索。

不要只记“圆角很大”“颜色很好看”，而要拆成可执行变量：

```text
页面唯一任务：让用户理解试用价值并开始试用
信息层级：结果承诺 → 3 个权益 → 价格与周期 → 主 CTA
主要控制：底部固定 CTA
信任信号：评分、用户数、可随时取消
风险点：默认选项不透明、价格单位过小、关闭入口隐藏
```

单张 Screen 适合解决布局与信息层级问题，但不能替代完整 Flow。付费墙看起来合理，不代表它出现的位置合理。

### 3. Element：研究一个组件的行业惯例

当问题缩小为“Tab Bar、进度条或主按钮应该怎么做”时，再研究 UI Element。

此时要提取**数字和规则**，不是感觉：

- 元素放在哪里，尺寸和留白大致如何？
- 有几个项目，图标与文字怎样组合？
- 默认、激活、禁用和错误状态怎样区分？
- 哪些变体在不同品类中反复出现？

研究顺序应当是：

```text
Flow 决定旅程
  ↓
Screen 决定页面任务和信息层级
  ↓
Element 决定控件的具体表达
```

反过来从一个漂亮按钮开始，很容易得到“组件精致，但整个旅程不成立”的产品。

## 六步研究法：从问题到设计规范

### Step 1：先写研究问题

一个研究 Pass 只回答一个明确问题，例如：

- 健身应用为什么常在 Onboarding 中先问目标再请求通知权限？
- 高营收语言学习应用通常把付费墙放在第一次练习前还是后？
- 记账应用的空状态如何让用户完成第一笔记录？

“看看同行怎么做”不是合格问题，它没有停止条件，也无法变成规范。

### Step 2：建立候选池

筛选 5 款左右候选应用，不只看营收，还要综合：

| 信号 | 用途 |
|------|------|
| 营收 | 优先发现商业机制值得研究的产品 |
| 下载量 | 判断模式是否经过大规模用户使用 |
| 评分与评价量 | 观察体验接受度，但警惕地区和历史版本差异 |
| 上线时间 | 区分成熟范式与较新的设计语言 |
| 与当前任务的匹配度 | 防止研究“数据好看但问题不同”的应用 |

### Step 3：按旅程顺序走完

完整查看候选应用中与问题有关的 Flow，不要随机抽几张图。按顺序记录每一屏的：

- 唯一任务
- 用户付出与得到
- 信息层级和主行动
- 页面呈现方式与返回行为
- 值得采用、需要警惕和仍未解决的地方

### Step 4：跨应用归纳品类语法

不要为每款应用分别写一篇赏析。把它们放在同一张矩阵里：

| 观察项 | App A | App B | App C | 结论 |
|--------|-------|-------|-------|------|
| Onboarding 步数 | 8 | 6 | 9 | 个性化问答占主要篇幅 |
| 权限请求时机 | 第 6 步 | 完成后 | 第 7 步 | 先解释价值，再请求权限 |
| Paywall 位置 | 首次结果后 | 引导末尾 | 首次结果后 | 结果后展示更值得测试 |
| 跳过入口 | 有 | 有 | 无 | 隐藏跳过不是稳定共识 |

把结论分为三类：

- **Table stakes**：赢家普遍采用的品类惯例，打破前必须有理由
- **Edge**：只有最佳样本做得好的细节，可形成质量优势
- **Opening**：多数竞品都处理不好的缺口，是你的差异化机会

### Step 5：写成设计规范

研究产物不是图片收藏夹，而是能交给设计师或 Agent 的约束：

```markdown
## Onboarding 设计规范

- 目标：在 6–8 步内完成目标识别、个性化和首次承诺
- 共同骨架：目标 → 当前水平 → 使用频率 → 计划摘要
- 权限：解释通知价值后再触发系统弹窗
- Paywall：优先测试在首次个性化结果之后出现
- 导航：完成与跳过都离开 onboarding stack，返回不可重新进入
- 我们的差异：把计划摘要变成可编辑承诺，不复制竞品文案或视觉资产
- 待验证：Paywall 位置必须通过实验验证，不把竞品营收当作因果证据
```

### Step 6：实现后回到真实设备验证

把参考模式变成自己的品牌、内容和交互，然后在模拟器或真实设备上走完整 Flow。检查长文本、空状态、加载、错误、深色模式、动态字号、返回路径和动效。

“参考了赢家”不是验收结果；你的实现仍然需要可用性、无障碍、性能和业务实验来证明。

## 两种使用路径：人工浏览与 Agent MCP

### 路径 A：人工浏览

适合快速探索和团队讨论：

1. 在 [AppLlama Apps](https://appllama.io/) 按品类、营收或下载量筛应用
2. 在 [Screens](https://appllama.io/screens) 按页面类型做横向比较
3. 在 [Flows](https://appllama.io/flows) 按完整旅程比较多款应用
4. 只保存任务所需的少量引用，并记录应用名、页面名和访问日期

### 路径 B：让 Agent 通过 MCP 研究

AppLlama 提供远程 MCP：

```text
https://mcp.appllama.io/mcp
```

官方同时提供两项开源 Agent Skill：

```bash
npx skills@latest add appllama/appllama-skills
```

- `appllama-usage`：定义如何搜索应用、遍历 Flow、研究 Screen 与 Element
- `appllama-app-design-skill`：把研究结果转为移动端实现和模拟器验证标准

一个合格的研究提示词应包含问题、样本标准、输出格式和停止条件：

```text
研究高营收习惯养成应用的首次 Onboarding。

先检查 MCP credits，再按营收、评分、下载量和任务匹配度选 5 款应用。
逐一走完它们的 Onboarding Flow，比较步数、每步索取与回报、权限时机、
Paywall 位置和导航语法。输出 Table stakes / Edge / Opening，最后写成
我们的 Onboarding 设计规范。不要复制文案和视觉资产；当新样本不再改变
结论时停止，并说明仍需实验验证的假设。
```

MCP 的使用边界：Pro 计划包含每月 1,500 credits；除 `get_credits` 外的调用会消耗 credits，媒体链接约 1 小时后过期。具体额度与计划可能变化，以官网为准。

## 研究纪律：避免从“证据”滑向“抄袭”

### 可以做

- 为一个真实设计任务研究少量相关应用、界面和 Flow
- 提炼共同骨架、信息层级、导航语法和品类惯例
- 在教学或评论中引用单张界面，并注明来源应用
- 用自己的品牌、内容和交互实现经过判断的模式

### 不应该做

- 批量抓取、镜像、缓存或重建整个图库
- 绕过免费/付费访问限制或速率限制
- 把竞品界面 1:1 复制进自己的产品
- 把高营收相关性写成“这个设计一定提升转化”的因果结论
- 用图库内容训练、微调、评测或索引机器学习模型

AppLlama 的条款明确说明：软件自动访问应使用官方 MCP；图库内容可用于研究、分析、参考和设计启发，但不能被批量提取或再分发。实际项目还要遵守原应用的商标与版权边界。

## 实操练习

选择一个与你当前产品最相关的 Flow：Onboarding、Paywall、Empty State 或品类核心 Flow。

完成以下交付：

1. 写出一个明确研究问题
2. 选 3–5 款应用，并说明为什么它们值得研究
3. 建立一张跨应用对比矩阵
4. 提炼 Table stakes、Edge 和 Opening
5. 写一份不超过 12 条的设计规范
6. 标出哪些结论是观察，哪些只是待实验的假设

推荐目录：

```text
research/<category>/
├── apps.md       # 候选应用、经营信号、选择理由
├── flows.md      # 按旅程顺序的观察记录
├── matrix.md     # 跨应用对比
└── spec.md       # 可执行设计规范与待验证假设
```

不要把大批截图长期归档到仓库。保留必要笔记、来源应用和 Screen ID；需要再次查看时，通过官方界面或 MCP 重新获取。

## 常见问题

**Q: 直接选择营收最高的应用不就够了吗？**

A: 不够。营收、下载量和评分只是筛选信号，还要看应用与你的问题是否匹配。高营收应用的设置页可能很普通，低营收但新品类更匹配的应用反而更值得研究。

**Q: 看多少张图才算够？**

A: 以“研究饱和”为停止条件：新样本不再改变设计规范时可以停止。官方 Skill 建议在单个 Screen 设计前研究 10–30 个相关样本；Flow 研究通常至少横向比较 3–5 款应用，并完整走完相关旅程。

**Q: 为什么不能只看 Dribbble 或 Behance？**

A: 它们适合视觉启发，但常缺少真实产品的流程顺序、状态变化、经营信号和导航行为。AppLlama 更适合回答“上线产品实际怎样解决”，两者可以互补。

**Q: 没有 Pro 计划还能学习这套方法吗？**

A: 可以。免费页面能浏览欢迎页和少量完整应用，你也可以把六步研究法用于 App Store、实际安装的应用或其他合规来源。MCP 与完整图库能提高效率，但方法本身不依赖单一工具。

**Q: 参考高营收应用，会不会让产品越来越同质化？**

A: 如果只复制共同模式，会。正确做法是保留 Table stakes 降低学习成本，再从竞品共同缺口中寻找 Opening。研究的目标是知道哪些惯例值得遵守、哪些选择可以有意识地打破。
