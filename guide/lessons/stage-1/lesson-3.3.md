# Lesson 3.3: `/subtask`——把执行过程移出主上下文

## 本课目标

- 理解 `/subtask` 为什么属于主动上下文管理，而不只是“并行执行”
- 掌握 forked subagent 的上下文继承、后台执行与结果回传机制
- 区分 `/subtask`、普通子代理、Skill、`/fork` 和 Agent View
- 学会写清任务边界，避免后台任务污染工作区或与主任务冲突

> **实操须知**：请新开一个 Claude Code session 完成本课练习，不要在教学 session 中直接执行。子任务完成后的报告会回到发起它的对话，可能打断课程节奏。

## 核心内容

### 主动管理不只是“事后压缩”

Lesson 2 和 Lesson 3 介绍了 `/clear`、`/compact`、`/btw` 与会话生命周期。它们解决的是不同层次的问题：

```text
/clear、/compact   已经进入主上下文的信息，如何清理或压缩
/btw               一个很小的侧问题，如何不写进对话历史
/subtask           一段较长的执行过程，如何从一开始就放到旁路
```

这带来一个更主动的判断：

> **上下文管理不只是删掉什么，更重要的是决定哪些过程根本不进入主线。**

搜索几十个文件、核对文档、运行测试、做独立审查，都可能产生大量工具输出和中间推理。主对话真正需要的通常只是结论、证据和下一步。

### `/subtask` 做了什么

基本语法：

```text
/subtask <要交给后台子任务完成的工作>
```

例如：

```text
/subtask 检查当前仓库用于生成微信公众号文章的 Skill；
只读，不修改文件；
返回主链路、文件路径、行号、规则冲突和优化优先级。
```

Claude Code 会执行以下流程：

```text
当前主对话
   │
   ├── 复制调用时的完整上下文
   │      对话历史、系统提示词、项目指令、模型、工具
   │
   └── forked subagent（后台）
          ├── 搜索文件
          ├── 读取材料
          ├── 调用工具
          ├── 分析和验证
          └── 把最终报告送回主对话
```

主对话不需要容纳子任务读取的全部文件和中间输出，只接收最终报告。你也可以在它运行时继续处理主线工作。

### 为什么 fork 之后还能节省主上下文

`/subtask` 会复制当前对话，因此它不是“零成本”。但复制发生在子任务自己的上下文窗口中，后续探索不会继续挤占主对话。

假设一次仓库审查需要：

```text
读取 30 个文件       大量上下文
运行 8 条检查命令     大量日志
反复核对 5 个判断     多轮推理
最终报告              30 行结论
```

直接在主对话执行，所有过程都留在主线上。使用 `/subtask`，主对话只保留：

```text
任务定义 + 最终报告
```

因此它最适合“**需要当前背景、执行过程很长、最终产出很短**”的任务。

### `/subtask` 与普通子代理的关键区别

Lesson 7 介绍的 Explore、Plan 和自定义子代理，默认从新的独立上下文开始，只接收父级给出的任务提示。

`/subtask` 是一个特殊的 **forked subagent**：

| 维度 | 普通子代理 | `/subtask` fork |
|------|-----------|-----------------|
| 对话历史 | 默认不继承 | 继承调用时的完整历史 |
| 任务说明 | 父级需要主动补齐背景 | 已经拥有当前对话背景 |
| 适合场景 | 独立搜索、专业审查 | 依赖当前讨论的独立支线 |
| 中间过程 | 留在子代理内部 | 留在 fork 内部 |
| 返回方式 | 摘要返回父级 | 最终结果回到原对话 |

判断口诀：

```text
不需要之前的讨论，只要独立完成       → 普通子代理
需要之前的讨论，但过程不该留在主线   → /subtask
需要持续和你来回决策                 → 留在主对话
```

### 不要把 `/subtask` 当成 Skill

两者的名字都可能出现在斜杠命令后面，但机制不同：

| 维度 | Skill | `/subtask` |
|------|-------|------------|
| 本质 | 可复用的专业操作手册 | 一次性的后台上下文分叉 |
| 执行位置 | 通常加载到当前上下文 | 新建 forked subagent |
| 主要价值 | 注入方法、规范和流程 | 隔离执行过程、保护主上下文 |
| 典型输入 | `/wechat-article` | `/subtask 审查 wechat-article 的规则冲突` |

二者可以组合：你可以让 `/subtask` 在后台调用某个 Skill，但“调用方法”与“开辟执行空间”仍是两件事。

> **容易混淆的一点**：Skill 自己也可以在 frontmatter 中声明 `context: fork`，让一套预定义流程在 fork 中运行；`/subtask` 则由你临时描述一次性任务。界面有时会显示 “forked skill”，那是运行时对这次 fork 执行的标签，不代表它来自项目的 `.claude/skills/` 目录。

### `/subtask` 与 `/fork` 的区别

当前 Claude Code 中，这两个命令都从现有对话分叉，但结果归宿不同：

| 命令 | 目的 | 完成后发生什么 |
|------|------|----------------|
| `/subtask <任务>` | 临时派出一项后台工作 | 最终结果自动回到原对话 |
| `/fork [任务]` | 创建独立的后台会话 | 新会话形成自己的工作线 |
| `claude --continue --fork` | 从历史会话复制出新会话 | 在新的 CLI 会话中继续探索 |

可以把它们想成：

```text
/subtask   派同事调查，回来向当前会议汇报
/fork      复制当前会议，另开一间长期会议室
```

如果你只是需要一份检查报告，用 `/subtask`。如果这条支线会持续开发、反复沟通或单独交付，用 `/fork` 或 Agent View 更合适。

### 工作目录不是自动隔离区

fork 的工具调用与对话上下文彼此独立，但默认仍从当前项目目录开始工作。

需要记住三个边界：

1. 子任务执行 `cd`，不会改变主会话的 shell 位置。
2. 子任务写入项目文件，可能直接影响当前工作树。
3. 主任务和子任务同时编辑同一个文件，可能互相覆盖或产生冲突。

所以只读任务要明确写：

```text
只读，不修改文件。
```

允许修改时要进一步限定：

```text
只允许修改 docs/api.md；
不要修改其他文件；
不要提交、推送或发布；
完成后返回修改清单和验证结果。
```

如果多个任务需要同时改代码，应使用独立 worktree 或 Agent View 的隔离机制，而不是让它们共享同一个工作树。

### 给子任务一份“小合同”

稳定的 `/subtask` 提示词包含四部分：

```text
/subtask
目标：要得到什么结果
范围：允许查看或处理哪些内容
边界：是否允许修改、执行、发布
交付：结果用什么格式返回
```

可直接复制这个模板：

```text
/subtask 完成以下独立任务：

目标：<最终要回答的问题>
范围：<目录、文件、时间或数据范围>
边界：只读；不修改文件；不执行外部发布操作
交付：先给结论，再列证据路径与行号，最后给下一步建议
```

任务描述越像一份可验收的小合同，后台返回的结果越容易直接使用。

### 选择哪一种上下文出口

| 当前需求 | 推荐工具 | 原因 |
|---------|---------|------|
| 问一个几十秒能回答的侧问题 | `/btw` | 不进入对话历史 |
| 做较长的独立调查，且需要当前背景 | `/subtask` | 继承上下文，只回传结果 |
| 做独立专业审查，不依赖当前历史 | 普通子代理 | 全新上下文，更少偏见 |
| 开辟一条长期平行工作线 | `/fork` | 形成独立后台会话 |
| 同时推进多个可交付任务 | Agent View | 集中查看、调度和隔离 |
| 给当前 Claude 注入固定方法 | Skill | 默认共享当前上下文；也可声明 `context: fork` |

```text
/subtask 检查当前仓库中与上下文管理有关的课程；
```

子任务运行时，在主对话继续问一个与主线有关的问题。观察：后台探索不会阻塞当前对话，完成后只返回汇总报告。

#### 练习 2：补齐任务边界

比较下面两条指令：

```text
❌ /subtask 看看测试有什么问题

✅ /subtask 运行 npm test 并分析失败原因；
   不修改代码和测试；
   返回失败用例、根因证据和建议修复顺序。
```

思考第二条为什么更安全：目标、权限和交付格式都可以验收。

#### 练习 3：判断是否应该分叉

为下面三个任务选择工具：

```text
A. 查询 package.json 里的 Node 版本
B. 阅读 40 个 Skill 并整理共同结构
C. 与 Claude 连续讨论新产品的定价策略
```

参考答案：

- A：`/btw`，问题很小，不值得创建 fork
- B：`/subtask`，读取量大、结果短，适合移出主上下文
- C：留在主对话，需要持续基于前文来回决策

## 常见问题

**Q: `/subtask` 是仓库里安装的 Skill 吗？**

A: 不是。它是 Claude Code 的内置命令，创建 forked subagent。仓库 Skill 是可复用的方法和工作流，两者可以组合但机制不同。

**Q: 子任务能看到我之前说过的话吗？**

A: 能。`/subtask` 继承调用时的完整对话上下文。但 fork 之后主对话新增的消息不会自动同步过去，所以任务所需的最终边界仍应在调用指令中写清楚。

**Q: 为什么不直接开一个普通子代理？**

A: 普通子代理默认不继承完整历史，适合背景独立的工作。任务依赖当前讨论、但执行过程又很长时，`/subtask` 可以省去重复解释背景的成本。

**Q: 子任务会修改我的文件吗？**

A: 如果它拥有写工具并且指令允许，它可以修改。默认工作目录并不等于独立 worktree，所以只读调查一定要明确写“只读，不修改文件”。

**Q: 输入 `/subtask` 后没有这个命令？**

A: 当前官方文档要求 Claude Code 2.1.212 或更高版本，并依赖 Agent View 能力。先检查 `claude --version`；如果版本过旧，请让 Claude 帮你升级并重新打开 session。

**Q: 它真的减少模型用量吗？**

A: 它主要保护的是主对话的上下文质量，不保证总 token 或配额更少。fork 自己仍会消耗模型资源。它的收益是把长过程隔离出去，让主线只保留可用结论。

## 相关概念

- **主动管理上下文**（Lesson 3）— `/subtask` 是“在信息进入主线之前分流”的策略
- **子代理系统**（Lesson 7）— 普通子代理默认使用全新上下文，forked subagent 是特殊分支
- **Agent View**（Lesson 7.2）— 适合多个独立长任务的后台调度与隔离
- **Git Worktree**（Lesson 3.2）— 多个写任务并行时隔离文件修改
- **Skill 系统**（Lesson 6）— 提供方法，`/subtask` 提供独立执行空间
